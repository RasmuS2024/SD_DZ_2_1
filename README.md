## О проекте
Консольное приложение для учета личных финансов. Позволяет вести счета, категории доходов/расходов и операции. Реализованы паттерны проектирования: Фабричный метод, Фасад, Команда, Шаблонный метод.

## Предметная область
Программа моделирует три основные сущности:
- **Счет** – хранилище средств с уникальным ID, названием и балансом.
- **Категория** – группировка операций по типу (доход/расход) с названием.
- **Операция** – движение средств с привязкой к счету, категории, суммой, датой и описанием.

## Реализованные паттерны проектирования

### 1. Фабричный метод
Изолирует логику создания объектов. Для каждой сущности создана отдельная фабрика:
- `AccountFactory` – создание счетов (с балансом, с ID, без ID).
- `CategoryFactory` – создание категорий доходов и расходов.
- `OperationFactory` – создание операций (доход/расход, с датой или без).

### 2. Фасад
Объединяет связанные методы в единый интерфейс, скрывая сложность сервисов. Реализованы фасады:
- `AccountFacade` – работа со счетами.
- `CategoryFacade` – работа с категориями.
- `OperationFacade` – работа с операциями.
- `AnalyticsFacade` – аналитика (отчёты по периодам, группировка по категориям).

### 3. Команда
Каждый пользовательский сценарий представлен отдельным классом, реализующим интерфейс `Command`. Это позволяет:
- Легко добавлять новые пункты меню.
- Строить меню автоматически на основе списка команд.
- Изолировать логику каждой операции.

Команды делегируют выполнение методам `CommandHandler`, что сохраняет единую точку для бизнес-логики.

### 4. Шаблонный метод
Применён для импорта данных из файлов разных форматов (JSON, YAML, CSV). Абстрактный класс `DataImporter` определяет общий алгоритм импорта (чтение, парсинг, сохранение). Конкретные импортёры (`JsonDataImporter`, `YamlDataImporter`, `CsvDataImporter`) реализуют только специфичную для формата часть – метод `parseFile`. Это обеспечивает единообразие обработки и упрощает добавление новых форматов.

## Архитектура и SOLID
- **Single Responsibility** – каждый класс имеет одну чёткую обязанность (модели – данные, репозитории – хранение, сервисы – логика, фасады – объединение, команды – сценарии).
- **Open/Closed** – сервисы работают через интерфейсы; новые реализации (например, другого хранилища) добавляются без изменения существующего кода.
- **Liskov Substitution** – наследование практически отсутствует, принцип соблюдается.
- **Interface Segregation** – интерфейсы сервисов и фасадов содержат только необходимые методы.
- **Dependency Inversion** – зависимости направлены на абстракции (интерфейсы), конкретные реализации внедряются через конструкторы.

## DI-контейнер
Все зависимости передаются через конструкторы (constructor injection), а сборка объектов выполняется в классе AppContainer. 
Этот класс выступает в роли простого DI-контейнера:
 - создаёт экземпляры репозиториев, сервисов, фасадов, фабрик, импортёров и экспортёров;
 - формирует граф зависимостей, передавая нужные объекты в конструкторы;
 - собирает список команд и передаёт их в MenuController.

## Измерение скорости выполнения пользовательских сценариев
В папке command реализован декоратор TimedCommand, который реализует возможность замера времени выполнения пользовательских сценариев, включая время ввода пользователем необходимых данных. <br>
В AppContainer реализован метод addTimedCommand, который в список доступных команд добавляет команду, обернутую в TimedCommand. <br>
Для примера, addTimedCommand используется в аналитических отчетах и экспорте/импорте. <br>
При запуске данных команд в консоли выводится время выполнения сценария.

## Проблемы при расширении
1. **Добавление новых типов счетов** (например, кредитный с отрицательным балансом) – потребует изменений в логике `AccountService` и `OperationService`, а также в моделях.
2. **Смена способа хранения данных** (с in-memory на реляционную БД) – затронет все репозитории, потребуется переписать их, хотя интерфейсы сервисов останутся неизменными.
3. **Добавление валют** – изменения в модели `BankAccount` (хранение валюты) и во всех сервисах, работающих с суммами и балансами.
4. **Сложные аналитические отчёты** – текущая архитектура не оптимизирована для агрегации больших объёмов данных; может потребоваться введение отдельного хранилища или кэширования.
5. **Поддержка многопользовательского режима** – потребует пересмотра всей модели данных и добавления контекста пользователя во все сервисы.

## Почему абстракции улучшили дизайн
1. **Разделение ответственности** – классы сфокусированы на своих задачах.
2. **Тестируемость** – модули легко тестировать изолированно (с моками).
3. **Гибкость** – можно заменять реализации (например, фабрики, импортёры) без влияния на остальную систему.
4. **Читаемость** – понятная структура, каждый паттерн решает конкретную проблему.
5. **Поддержка** – изменения локализованы, минимизированы побочные эффекты.
